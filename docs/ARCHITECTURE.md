# Threelanguage — Архитектура (v0.1, для ревью)

## Главный принцип: «общее ядро, два равноправных клиента»

Требование «оба приложения равноправны» + «нативно, без WebView» + «масштабирование до
японского/китайского/корейского» диктует такую схему:

```
                 ┌──────────────────────────────┐
                 │   shared core (логика игры)  │  ← ОДИН свод алгоритмов
                 │  SRS, скоринг, АФК-таймер,   │     (спека + эталонные тесты)
                 │  генератор сессий, прогресс  │
                 └──────────┬───────────────────┘
              portability: одинаковая логика на обеих платформах
        ┌───────────────────┴────────────────────────┐
        │                                            │
 ┌──────▼─────────────────┐            ┌─────────────▼──────────────┐
 │ Android (Kotlin/Jetpack │            │ Desktop (C++20 / Qt6)      │
 │ Compose, Room,          │            │ SQLite(C++), QPainter      │
 │ TextToSpeech            │            │ pixel-perfect NEAREST,    │
 │                         │            │ без браузеров/WebView     │
 └──────────┬─────────────┘            └─────────────┬──────────────┘
            │            REST + sync-файл             │
        ┌───▼─────────────────────────────────────────▼──┐
        │         Backend (FastAPI + PostgreSQL)          │
        │ курсы/деки, аккаунты, синхронизация, статистика  │
        │ темпа, аудит оценок уроков, TTS-прокси для CJK   │
        └──────────────────────────────────────────────────┘
```

### Почему не Flutter и не KMP (и что пересмотреть на ревью)

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **Flutter** | один UI-код | Skia-прослойка вместо нативного виджета-рантайма; desktop под Debian слабее; тяжёлый рантайм | ✗ против духа ТЗ («никаких браузеров», нативность) |
| **KMP (Kotlin Multiplatform)** | общее ядро Kotlin → Android + Desktop(JVM) | Desktop = JVM-зависимость, UI через Compose MP ещё сырой на Win/Debian | ⚠ запасной вариант (см. компромисс ниже) |
| **Выбрано: спецификация ядра + 2 нативных порта** | Android чистый Kotlin/Compose, Desktop чистый C++20/Qt6; оба легковесны и по-настоящему нативны; расхождения ловятся общими golden-тестами | логику писать дважды | ✓ настоящее равноправие |

Компромисс против «писать дважды»: ядро формулируется как **формальная спека
(`shared/algorithm/`)** + **эталонный Python-референс (`shared/algorithm/reference.py`)** +
единый формат данных. Оба клиента обязаны проходить один прогон fixture-тестов
(вход → ожидаемый выход). Если на ревью захочется меньше дублирования — миграция на
KMP-core не ломает ни формат данных, ни бэкенд.

### Равноправие клиентов (обязательное)
- Один формат сейва: `.threesave` (ZIP: `manifest.json` + `state.db`(SQLite) + `settings.json`).
- Один REST API; клиенты «толстые» в игровой логике, сервер — источник истины для курсов и мультидевайс-синхронизации (event-log, last-write-wins).
- Чек-лист паритета экранов ведём в `docs/PARITY.md` (заполняется при реализации).

## Данные и контент (откуда брать — предложение)

1. **Wiktionary dumps** (CC BY-SA) — слова, переводы между языками, IPA, примеры.
2. **Частотные списки**: OPUS/OpenSubtitles frequency lists (CC), COCA-top для EN;
   для CJK свободные структурированные словари: **JMDict** (JA, CC BY-SA),
   **CC-CEDICT** (ZH, CC BY-SA), **KAIST/korean-english-db** (KO).
3. **Anki-совместимый импорт (.apkg)** — пользователи приносят готовые колоды; UGC-курсы на сервере версионируются.
4. **TTS**: Android — системный `TextToSpeech`; Desktop — `espeak-ng`/голоса ОС; для CJK — серверный TTS-прокси с кэшем mp3 (мобильные TTS для ja/zh/ko слабые).

MVP-костяк: EN↔RU, ES↔RU, DE↔RU по 2000 частотных слов, собранных скриптом
`backend/tools/build_decks.py` (пишется после ревью источника).

## Масштабирование под CJK (ja/zh/ko) — закладываем сейчас

- Модель карточки: `text` + `reading` (kana/pinyin/romaja) + `senses[]` + `audio_refs[]` + `script_tag`. Ни одно поле не предполагает латиницу.
- Письменный ввод сравнивается после Unicode NFKC-нормализации; диакритика (pinyin tones, áéíóú) — через decompose+match по шаблону. Stroke-order (kanji/hanzi) — v2, данные KanjiVG (CC BY-SA).
- Корейские частицы (josa) и японская морфология решаются на стороне словаря senses, клиент показывает готовые поля.
- Шрифты desktop: бандлит Noto Sans CJK + IPAex; пиксельный шрифт — только для UI-вывесок, текст заданий обычный.
- Postgres: UTF-8 везде, pg_trgm-индекс по reading; citext только для latin-языков.

## Хранилище

- Клиент: SQLite (Android Room / desktop sqlite3), единая DDL `shared/schema/state.sql`.
- Сервер: FastAPI + SQLAlchemy(async) + PostgreSQL + Alembic; Redis опционально (rate-limit).
- Синхронизация: append-only `events` (карточка-стейдж, попытки, сессии, настройки); LWW по `server_seq`; экспорт того же event-log в `.threesave`.

## Модули клиента (одинаковая декомпозиция)

```
core/  srs | scoring | afk | session | placement | storage   (kt + cpp, по одной спеке)
ui/    android: Compose-экраны Home/Lesson/Micro/Stats/Settings/Placement/MascotView
       desktop: Qt6 те же экраны 1:1, QPainter c NEAREST-скейлингом спрайтов
```

## Открытые решения (ответь на ревью)
1. Ядро: две реализации по спеке (предложено) vs KMP-core.
2. Desktop GUI: Qt6 (LGPL, предложено) vs GTK4 vs wxWidgets.
3. Костяк колод: Wiktionary+OPUS+JMDict/CEDICT (предложено) vs анки-наборы vs ручной труд.
4. TTS для CJK: серверный прокси (предложено) vs только голоса ОС.
5. Аккаунты: гость+локальный сейв с опциональной регистрацией (предложено) vs обязательные.
6. Сложность SRS: FSRS-lite (предложено, docs/SRS.md) vs SM-2 vs Anki-default.
